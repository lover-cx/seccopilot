# SecCopilot：一个会说"我不知道"的安全研究助手

> 2026 Qoder 高校创造力大赛 · StudyHack 学习科研赛道（天池赛题 532395）
> 在线体验：https://seccopilot-kpa8w0w9u7e.qoder.zone
> 一句话：把 CVE 漏洞库、MITRE ATT&CK、CWE 弱点目录、arXiv 安全论文接进一个问答助手，每条回答都能点开原始权威页面。

## 一、为什么做这个

安全研究日常是这样：想看一个漏洞，开 NVD；想知道攻击手法，开 attack.mitre.org；想找缓解措施，再开 CWE；想看看学术界最近做了什么，开 arXiv。四五个标签页来回切，最后自己拼结论。

直接把问题丢给通用大模型会更省事吗？我们实测过，结果是这样：问"2026 年新披露的 Log4j 漏洞有哪些"，不开搜索的模型回答"现在是 2024 年，2026 尚未到来"；问"CWE-79 是什么弱点"，它可能给你一个 CWE-791。安全场景里编造一个 CVE 编号不是小 bug，它会让人拿着不存在的编号去写报告。

所以 SecCopilot 的目标不是"答得像"，而是**答得可核验，且知道边界在哪**。

## 二、架构：一个域名装下前后端

```
浏览器（React 19 + TS + Tailwind 4，Vite 8 构建）
      │  同源 fetch，只传问题与模式
      ▼
Qoder Sites Serverless Function（Deno edge，多文件）
  ├─ lib/kb.ts        Supabase pgvector 检索 + 编号精确匹配 + NVD 实时补查
  ├─ lib/dashscope.ts embedding / 生成 / 联网搜索三种上游调用
  ├─ lib/chat.ts      三层来源编排与引用合成
  └─ lib/routes.ts    stats / cve / attack 只读端点
      ▼
Supabase（PostgreSQL + pgvector，1024 维）  +  DashScope（text-embedding-v3 / qwen-flash）
```

选 Qoder Sites 的原因很实际：这个项目原本要写 FastAPI、配 CORS、找台服务器、弄 HTTPS 证书。现在前端 `dist/` 和 Deno 函数一起上传，密钥放在 Sites 的 Secrets 里，前端永远拿不到 Supabase 与模型密钥，`git clone` 也不会带出任何密钥。整条发布链路就是 `prepare_site → publish_site` 两次调用。

## 三、核心设计：三层知识来源，各说各的话

| 层 | 内容 | 什么时候用 | 引用怎么标 |
| --- | --- | --- | --- |
| L1 本地精编库 | ATT&CK / NVD 精选 / CISA KEV / CWE / arXiv，共 5,397 条 | 默认都先查它 | `[L1]`，标题+可点击 URL+相似度 |
| L2 实时上游 | NVD API 2.0 现查 | 本地没有这个 CVE 编号时 | 标"本次实时查询上游官方库" |
| L3 网络检索 | DashScope `enable_search` | 本地命中不足，或问题涉及时效 | 单独一组 `[1..n]`，标注"未经知识库校验" |

三件事我们认为必须分开做，否则整个产品就是假的：

**1）来源不能混着引用。** 网络结果和社区博客永远不和 NVD、MITRE 官方条目放在同一组里，UI 上分两块，模型提示词里也明确"网络来源注明(网络检索)"。

**2）要不要联网是代码判断的，不是模型自觉。** 前端有三态开关：自动联网 / 强制联网 / 仅知识库。`仅知识库` 用于复现和答辩演示，`强制联网` 用于对比。

**3）"没查到"必须说出来。** 响应里有 `coverage` 和 `note` 两个字段，`note` 直接告诉用户本题是本地库回答、网络检索回答，还是知识库未覆盖。演示时最有说服力的一幕，就是把联网关掉问"2026 年 Log4j 新 CVE"——它回答"知识库未有效覆盖"，而不是编一个编号。

## 四、数据：870 → 5,397 条，全部来自官方一手来源

| 类别 | 条数 | 来源 |
| --- | --- | --- |
| CVE 漏洞 | 1,774 | CISA KEV 官方目录（含修复期限、是否被勒索软件利用）+ 精选 NVD 高危条目 |
| ATT&CK | 867 | MITRE ATT&CK 官方（战术/技术/检测/缓解） |
| CWE 弱点 | 956 | MITRE CWE 5.0 官方 XML |
| 安全论文 | 1,800 | arXiv cs.CR 最新提交 |

我们**没有**把 NVD 全量 42 万条灌进去。算过 embedding 成本，也算过检索噪声，更关键的是：把实时数据变成静态快照，恰好违背"时效性"这个真实需求。所以策略是精编权威小库 + 冷门编号现查上游 + 时效问题联网。

采集与入库脚本在 `data/` 下，可安全重跑：按语义主键（CVE 编号 / CWE 编号 / arXiv ID）去重，向量结果缓存到 `data/phase2_emb.jsonl`，中断续跑不会重复计费。本次 4,527 条新数据入库失败 0 条。

## 五、踩过的坑（这部分对我们价值最大）

**坑 1：OpenAI 兼容模式拿不到搜索结果。**
DashScope 兼容模式即使开了搜索，响应里也没有 `search_info`。必须走原生协议 `/api/v1/services/aigc/text-generation/generation`，加 `enable_search` + `search_options{search_strategy:"max", forced_search, enable_source, enable_citation, citation_format:"[<number>]"}`，来源在 `output.search_info.search_results`。证据是 `usage.plugins.search.count = 1`、input_tokens 从 45 涨到 6,208。

**坑 2：本地资料放错了轮次，联网检索就被带偏。**
把检索到的知识库正文塞进 user 轮，联网检索的搜索词会被老条目的编号（CVE-2021-44228）吸走，2026 年的新漏洞再也搜不出来。做过 A/B：正文移到 system、user 轮只留原问题，才稳定拿到当年编号和修复版本。代价是 input_tokens 从 6.5k 到 8.3k、延迟从 3.1s 到 5.4s——我们认为值得。

**坑 3：pgvector 的 IVFFlat 默认几乎不探测。**
索引是 `lists = 100`，而 `ivfflat.probes` 默认为 1，一次只扫约 54 行。实测同一个向量：`category_filter=NULL` 时问 "T1059" 返回 **0 行**，限定 `category='attack'` 却返回 200 行；问"量子纠缠"只回 8 行。原因是加不加分类条件走了不同执行计划。修复是把 `ivfflat.probes` 提到 100（本表 5 千行，精确检索仍是毫秒级），并把相似度门槛写成显式参数（`supabase-retrieval-fix.sql`）。

**坑 4：相似度阈值分不开"库内"和"库外"。**
我们原本想用"最高相似度 < 0.35 就去联网"。实测 11 个问题后发现这条路不成立：库内问题 top1 是 0.576 / 0.646 / 0.686 / 0.722，库外问题是 0.571（"WiFi 密码忘了"）/ 0.573（"项目内部仓库地址"）/ 0.630（不存在的 CVE-9999-0000）。区间完全重叠——多语言向量对"话题相近"和"真正命中"本来就分不开。改成只认两种可靠信号：编号/战术**精确锚点**，或语义分高到不像巧合（≥0.65）。

**坑 5：短编号必须精确查，不能靠语义。**
"CWE-79 是什么弱点"的语义 top1 是相似度 0.691 的 CWE-829，正确条目压根排不进来。现在问题里出现 `CVE-`、`CWE-`、`T####`、arXiv ID 一律走精确检索，相似度记为权威锚点。

**坑 6：Qoder Sites 的密钥命名有保留前缀。**
`SUPABASE_*`、`POSTGRES_*`、`QODER_*` 和 `DATABASE_URL` 是平台保留名，函数里读不到，我们改成 `APP_SUPABASE_URL` / `APP_SUPABASE_ANON_KEY`。另外函数目录支持多文件，但相对导入必须写全 `.ts` 扩展名。

**坑 7：参数写错会静默换掉被测对象。**
`scripts/eval.mjs` 的 `--only=` 一直是"只跑一种模式"的意思，今天有人把它当题目过滤器用了（`--only="微软 Office 漏洞"`）。未知值传到 Function 侧被 `normalizeMode` 归成 `auto`，脚本一声不吭：以为在跑一道题，实际跑完了整套 21 题，而且留档里每行的 `mode` 字段写着那个假模式名——这份数据谁也不能用，因为它测的既不是 `off` 也不是 `on`，而我们自己也没看出跑偏了，直到检查留档才发现。那份误跑出来的留档已经删掉（它不属于任何一个能标注的版本）。现在脚本里三处硬校验（外加下面那条来源声明的兜底）：`--only=` 只接受 `off|on|auto`；`--grep=` 才按关键字取子集，零命中直接退出；`--grep` 没配 `EVAL_JSON=` 时拒绝运行——子集留档默认会覆盖 `docs/eval-report.json`，而那份文件是现在这份 `docs/eval-report.md` 的来源证据（装的是"闸门版第二遍"那 42 条回答；线上已发布版本的证据在 `docs/eval-archive/deployed-prompt-only-2026-11-12.json`，一题的样本绝不能把整轮证据换掉）。**参数错误不该静默改变实验对象**：同一类事在这份稿子里已经撞到第五次（有 bug 的探针、判分器误伤、`stats` 把失败算成 0、这次的参数误用、以及下面这条 `--rescore` 的头部误标），共同点是工具出错时给出的东西看起来完全正常。

上面这条我们自己又犯了一次，而且犯在写稿的当天：用 `--rescore` 重算留档时没带 `SITE=`，脚本就用了默认的线上站点写报告头部——于是"本地 harness·闸门版·第二遍"那份留档在报告里被标成了"线上已发布版本"。数字一个都没变（`--rescore` 不打模型），**变的只有那句来源声明**，而这正是别人复核时唯一要看的一句话。修法是让留档自己声明来源：跑完把 `meta.site`（以及模式、题量、是否 rescore）写进 JSON，`--rescore` 生成头部时只认留档里的 `meta.site`，与本次 `SITE` 不一致就打印警告并按留档写；旧格式留档没有 `meta.site` 时也打印警告，而不是假装知道。已用同一份留档连跑三次验证：修好之前那次（不带 `SITE=`）就是静默写成了线上站点；修好后第一次带 `SITE=http://127.0.0.1:8000` 运行，脚本提示"留档没有 `meta.site`（旧格式），本次沿用 `SITE`"并把来源补写进留档；第三次再故意不带 `SITE=` 重跑，脚本提示"留档记录的被测对象是 `http://127.0.0.1:8000`，本次 `SITE` 是线上站点；报告按留档写"，头部输出仍是本地 harness——也就是说现在漏传参数只会留下一条警告，不会再改变来源声明。

## 六、怎么证明它没坏

- **29 项回归测试**直接打接口：统计口径求和一致、ATT&CK 战术过滤与 `T1059` 精确查询、CVE 的 severity/CVSS 元数据、KEV 字段前缀、联网响应契约字段、CWE 编号精确锚定、域外问题不得声称本地覆盖、`mode=off` 的回答不得声称做过网络检索、时效题必须以当天日期为基准、`mode=off` 不得把"本地库没记录"答成"现实中不存在"、问某阶段技术时不得列入别的技术、"在野利用"必须拿得出 KEV 证据；另有 3 项纯函数用例（`localTimeGapFacts` / `dropOffTacticDocs` / `kevFacts`）不打模型也能跑。`SKIP_LLM=1 npm test` 跑 12 项、跳 17 项，2026-11-12 结果 12/12 绿、零模型费用。

  完整套件（含 17 项要打模型的用例）我们不写"29/29 通过"这种单点数字，只写跑了几次、每次红在哪：**2026-11-12 在本地 harness 上跑了 5 次——前三次 27/29，判分口径修正后第四次 29/29，下午上游网络来源变空之后第五次又是 27/29，而每一轮红的都不是同一对**（`SITE=http://127.0.0.1:8000 npm test`，被测对象就是仓库里这份 `functions/`）。要说清楚：前四轮的输出只在终端里看过，只有第五轮留了日志（`dev/test-run5.log`）——这个落差本身就是我们后来要求每个探针都落文件的原因。把每一轮的回答原文和请求翻出来看，根因有三个：

  其一是**真缺陷**：`stats` 的分类计数在 `functions/lib/routes.ts:25` 被 `catch { return 0 }` 兜住，上游超时或并发排队时那一类就静默变 0——有一轮跑完 `paper` 报 0，分类求和 3597 对不上 total 5397，用例把它抓出来了；第五次那轮更极端，五类里只有 `cwe` 拿到数，分类求和 956 对 total 5397（`dev/test-run5.log`），而单独重打 6 次 `action=stats` 又是第一次 `total: 0`、后五次 5397。**HTTP 200、字段齐全、数字是错的**，这比报 500 危险得多——用户看到的是"库里只有 0 条"。同一时间单独连测线上站点 3 次，返回的都是正确的 5,397，所以这不是"线上在漏数"，而是"漏数的时候没人会知道"：一个会把"取不到"伪装成"没有"的接口，在安全场景里跟伪造数据同罪。改法要么失败就返回 502，要么一次聚合查询消除部分失败，两种都会动响应契约，所以先记在这里没有动代码。

  其二是**判分器自己误伤**，而且是两条不同的用例轮流出红：KEV 那条把"该编号未经 KEV 确认、不属于在野利用"这种本身就在否定的句子当成违规；全局否定那条把"因本地知识库在 2026 年内无新增条目，无法确认"——语义完全合格的诚实回答——判成"声称现实中不存在"。修法不是删用例，是把口径改准并同时钉住两个方向：KEV 判定改成整句里出现否定措辞就豁免；全局否定改成**按句**判定，只有句子没有限定在"本地知识库/本地库/本地资料"时才判红，并在同一条用例里放两个样本做自检——线上实测到的"目前无 2026 年新披露的 Apache Log4j 相关 CVE"必须仍判红，限定在本地库的那句必须判绿。改完之后才是上面那个 29/29。同一套用例打到线上已发布版本仍有几项红——凡依赖那三段代码兜底的都过不了，因为发布通道今天没通过（见本节末尾）。这个差别正是要说清楚的：用例红，能定位到"代码没上去"，而不是"代码不管用"。
  其三是第五次才冒出来的，而且**不是我们的代码**：`chat：响应含联网搜索契约字段` 从下午起稳定红，因为它断言 `web_sources.length > 0`，而这段时间上游的搜索插件执行了却不返回来源清单（0/10 次采样有来源）。我们拿请求直接打原生协议把性质定住了（见本节末尾第 8 条缺陷）。这条用例的断言对象本身写错了：它把"插件执行成功"和"搜索返回了来源"混成一件事，所以正确的修法不是放宽它，而是改成"空来源时不许声称结合了网络检索"——这条改动会动用户可见文案，等确认后一并改。
- **21 题对照评测**（`scripts/eval.mjs`）同一批题跑 `mode=off` 与 `mode=on`，自动判四件事：知识库内题的引用是否命中期望编号/官方域名、时效题是否命中该题的 ground truth、域外题是否正确承认未覆盖、以及**幻觉检测**——回答里出现的 CVE/CWE/T 编号若在所有来源标题与 URL 中都找不到，就标为可疑待复核。

但第二遍的 `on` 比线上低了一题，这题必须写清楚，因为它是我们自己新加的闸门没能拦住的那一类：**"2026 年被 CISA 确认在野利用的微软 Office 漏洞有哪些"**，线上版答出 CVE-2026-21509（KEV 收录 2026-01-26）与 CVE-2026-124194（KEV 收录 2026-11-10），判通过；闸门版第一遍把 21509 写成"虽被列入 KEV 目录，但资料未说明其在野利用的具体情况"——编号还在，判分器按包含关系判通过，结论其实已经错了；第二遍干脆不提 21509，直接判不合格。这一度让我们以为是检索不稳定，于是专门写了探针去查（`dev/probe-kevgate.mjs`）：**这道题的检索其实每次都一样**——连问三次，回来的都是同样五条 Microsoft Office 条目，`kevFacts` 三次都清楚输出"标注的编号：…CVE-2026-21509（收录 2026-01-26）…"。事实算对了照样被模型在联网那一侧扔掉，所以结论只能落在"算事实不等于强约束"上（详见本节末尾缺陷 7）。所以我们没把闸门版写成"全面优于线上版"：它修掉了全局否定与跨阶段混入，两遍 `off` 都是 21/21，可疑编号从 25 降到 22 / 15；代价是 KEV 这道题的遵守率不稳——今天在这台机器上把这道题的 `mode=on` 采了 10 次（`dev/kev-on-1.txt`~`kev-on-3.txt`、`dev/kev-on-batch.json` 6 次、`dev/eval-grep-check.json` 1 次），10 次全都列出 21509 并给出它的 KEV 收录日期；可两份留档那 2 次一次降级、一次整条丢掉（12 次采样 2 次不照闸门说），第二遍就因此少了一题。**这里要撤回我们自己写下的一句话**：稿子早先的版本说"`off` 4 次里 1 次过度推脱"，回查留档后发现那句"本地知识库未覆盖 2026 年的该主题"出现在 **Log4j** 那道题的 `off` 回答里，而在那里它恰恰是正确行为（库里确实没有 2026 年的 Log4j 条目）；Office 这道题的 `off` 今天留档重跑 4 次全部正确（`dev/kev-off-batch.json`）。这条撤回值得单独写出来，因为它就是我们一直在批评的那种错——**把一次没留档的终端输出当成结论**，而那句话听起来完全合理。发布通了以后第一件事是把它改成现查 CISA 目录、并对回答做硬校验，然后整张表重跑。

第一栏的数字来自 42 次线上回答，正文都留档在 `docs/eval-archive/deployed-prompt-only-2026-11-12.json`；报告头部标了 `--rescore`，即时效题按修正后的判分口径重算、没有重新调用模型。闸门版两份留档分别是 `docs/eval-archive/local-guards-run1-2026-11-12.json`、`local-guards-run2-2026-11-12.json`（现在这份 `docs/eval-report.md` 用的是第二遍，也就是分数更低的那遍）。第二栏没走线上，是因为发布通道今天一直没通（见本节末尾），而那三段兜底逻辑只在 Function 内部生效，拿线上版本去测它们等于测了个不存在的东西。做法是用仓库自带的 `npm run dev:function:node` 在本地跑同一份 `functions/`：`dev/function-node.ts` 起一个 Node HTTP 服务，把 `Deno.env` 映射到 `data/.env`，Supabase 检索、DashScope 生成、NVD 实时上游全部是真实网络调用（Node 24 要 `NODE_USE_ENV_PROXY=1` 才认代理变量；Supabase 走本机 Clash，DashScope 与 NVD 用 `NO_PROXY` 绕开）。代价要说清楚：第二栏量的是**源码的行为**，不是**站点当前的行为**，所以报告头部把被测目标原样写成 `http://127.0.0.1:8000（本地 harness……）`。发布通了以后要重跑一遍线上，这张表的第二栏才能搬到第一栏的位置。

**这一列今天单独看会骗人。** 上表"触发联网"统计的是响应里的 `search_used`，而它的含义是"上游搜索插件执行过"（判据是 `usage.plugins.search` 有值），**不等于"带回了可核验的网络来源"**。我们把请求直接打 DashScope 原生协议定性（`dev/probe-websearch-shape.mjs`）：`usage.plugins.search` = `{"count":1,"strategy":"max"}`，而 `output.search_info.search_results` 是**空数组**。这道 KEV 题今天下午 `mode=on` 连采 10 次，`web_sources` **10 次全是 0 条**；换 4 条不同问题、`auto` 与 `on` 两种模式，同样 0 条。而同一台 harness 在 14:47 那一轮，21 道 `on` 题的网络来源每条是 1~5 条——也就是说今天重跑整张表，`on` 那行的"触发联网 21"会变成"21 次联网、0 条来源"，因为它量的一直是插件执行次数而不是来源数量。所以我们把"联网效果"这种说法从报告里拿掉了：`触发联网` 必须和留档里的 `nWeb` 一起读，单看前者会把"没带回来源"读成"检索成功"。界面上这一点更直观——网络来源区块因为列表为空不渲染（`src/components/ChatPanel.tsx:232`），而 `note` 那句"结合本地知识库与网络检索作答"无条件显示（同文件 261 行），访客看到的就是一句"结合了网络检索"却一条都点不开；修法记在本节末尾第 8 条缺陷，它要动用户可见文案，等确认。

改前基线（`docs/eval-report-baseline.md`）是 `off` 13/20、`on` 17/20，知识库内题只有 83%。差距全部来自上面坑 4、坑 5 的两处修复，以及把 `match_documents` 的 IVFFlat `probes` 从默认 1 提到 100。

**为什么第二栏不是线上数字：发布通道今天没通过。** 从 11-10 起，`prepare_site` 的服务端校验一直停在 `verify_artifact` 直到超时，`last_error_code` 始终是 `task_deadline_exceeded`，11-12 这一天 5 个不同 actionId 全部同样失败（11-10 也撞到过同一条死线）；同一目录、同一份构建产物在此之前的发布是正常成功的（站点现在公开可访问，`deploymentId` 与 `releaseId` 就记在 `.SecCopilot.qoder.site` 里），本地 `tsc -p tsconfig.functions.json` 也一直是干净的，所以这不是把同一份错误代码上传了 5 次。我们停在这里没有继续刷重试——队列不通时重试只是烧时间。结果是：线上跑的还是"只改提示词"那一版，三道代码闸门只在本地 harness 上被测过。想复现这个本地测量，仓库里就有全部所需脚本（见"三十秒复现"），不需要我们的站点。

### 先说一个我们自己踩的坑：指标会骗人

上面这张表不是第一版。第一版跑完，`off` 模式的时效题显示 **100%**——比修好检索之前的 20% 好得离谱。我们没有庆祝，而是把 42 次回答的正文逐条读了一遍，发现是**判分正则在骗我们**：那条正则只要求回答里出现 `CVE-2026-\d{4,7}`，于是问 Log4j 时模型答了 Tomcat 的 CVE-2026-34486 也算通过；问"本周"时把 8 月的 KEV 收录记录说成本周也算通过。

顺着回答往下读，又挖出四个真实缺陷，都不是检索问题（后面逐条验编号时又暴露出三个，见"那些可疑编号"一节）：

1. **`mode=off` 会谎称联网。** system 提示词里有一条不分模式的措辞："两类资料都不足时明确说'知识库与网络检索均未覆盖'"。可 `off` 模式根本没联网，于是线上真的出现过"知识库与网络检索均未覆盖"这种对本系统行为的虚假陈述。改成按模式给措辞。
2. **模型不知道自己身处何年。** 回答"本周有没有新漏洞"时写过"当前为 2024 年 4 月"。现在由 Function 侧按北京时间算出当天日期注入提示词，修完之后 `off` 模式会明确说"本地知识库最近一条是 CVE-2026-34486，KEV 收录于 2026-08-04，超出本周范围，无法确认本周新增"；`on` 模式则直接给出"本周（2026年11月3日至11月10日）"再列具体编号。
3. **把"本库没记录"说成"现实中不存在"。** `off` 模式问"2026 年新披露的 Log4j CVE"时，回答里出现过这样一句："目前无 2026 年新披露的 Apache Log4j 相关 CVE"。本地库确实没有这批条目，但这句话的性质完全不同——它是对现实的全局否定，用户照着写报告就会漏掉真实存在的 CVE-2026-34477~34481。第一版修法是在提示词加规则："资料里没有只等于本库缺记录，不等于现实中不存在"。加了之后线上连测 3 次都对，我们准备收工——回归套件第 4 次采样又复发了。**对小模型讲抽象道理是压不住的，得把它能照抄的事实算出来**：现在由 Function 侧按条目正文里的日期核算"该时间窗内命中的条目数为 0""主题词全部命中的最近一条是 2023-05-22""距今 100 天（今日 2026-11-12）"，注进 system 让它照着承认。两个细节值得说：主题词必须**全部**命中同一条目，因为本地库里有 2026 年的 Apache Tomcat/ActiveMQ，只按"有没有 2026 年条目"判断会把缺口错误地点亮；而"最近/最新/目前"这类模糊时间词**不触发**这段兜底——本地 KEV 目录本身就是近期快照，误触发会把能正常回答的题变成拒答。
4. **版本号来自模型记忆，角标却挂给权威来源。** 同一次抽查里，回答把 CVE-2021-45046 的修复版本写成"2.17.1 及以上版本 [L1]"，而我们回查 `[L1]` 那条的原文，只有一句 `Apply updates per vendor instructions`。这个版本号恰好是对的，但"来源没写、角标挂上"正是安全场景里最难被发现的一类错误——它让一个未经证实的数字看起来有权威背书。现在提示词明确规定：资料没给版本号就照实说"官方未公布具体版本号，仅要求按厂商说明更新"，且这种句子禁止挂 `[Lx]`。这条只能靠抽样发现，判分器看不见（响应体只回来源标题，不回了正文），我们把它如实记成"抽样验证"，不冒充自动化覆盖。

判分口径也随之改成逐题 ground truth（报告末尾"时效题基准"表里每条都对过 NVD 接口），并且把回答原文一并存进 `docs/eval-report.json`——不然下次判错无从复核。"承认自己不知道"判为通过：这类题考的是时效覆盖，不是措辞。

判分器自己也错过一次，而且方向相反：`failIf` 原本是整篇匹配 `2026-0[1-8]-`，于是修好之后的标准答案"最近一条是 CVE-2026-34486，KEV 收录于 2026-08-04，**不在本周（2026-11-12）范围内**，无法确认"被误判成不合格——那一次 `off` 有两道时效题挂掉，一道是这个判分误伤，另一道是真缺陷。原则还是那句话：**把旧日期说出来不是错，把它当作本周才是错**。改成按句子切分判定：只有出现旧日期、且同一句里没有任何限定表述（不在/超出/早于/无法确认……）才算不合格。这一项修完，`off` 的时效题从 60% 回到 80%，前面表格里用的就是重算后的数；剩下那一道（Log4j 2026）是真缺陷，没有靠改判分把它"改"没。

这条改动不用重跑模型就能验证：判分是纯字符串逻辑，直接拿留档的回答原文重新评分（`node scripts/eval.mjs --rescore`，`EVAL_JSON=` 指定读哪一份）——旧算法判 `off` 不合格，新算法判合格，`on` 两种算法都合格。之所以值得为它加一个模式：改一次判分口径就要重打 42 次模型的话，人就会倾向于不改，而判分错恰恰是最该改的那种错。踩这个坑时还顺带发现一个更阴的写法问题：`new RegExp("CVE-2026-\d{4,7}")` 在 JS 里会先被字符串转义吃掉一层反斜杠，变成 `CVE-2026-d{4,7}`，永远匹配不到，而字面量 `/CVE-2026-\d{4,7}/` 是好的。核对判分逻辑时要用正则字面量，别拿临时脚本的假阴性当结论。

同一个判分器第二次骗我们，方向还是反的："本周有没有新披露的高危漏洞"这一题的"承认缺口"写法只列了 `无法确认本周|不能确认本周|无法确定本周` 三种连续写法。本地闸门版的回答是"本地知识库未覆盖近 7 天的新增条目，无法确认，需开启联网检索才能确认"——语义完全合格，字面却不匹配，于是被记成不合格，`off` 时效题停在 80%。这条不是产品缺陷，是判据欠包含；改法是要求"缺口承认词"与"本周/近 7 天"**同句共现**，不接受只说"无法确认"的泛泛推脱。关键是改完要把**两份留档都用同一套新口径重算一遍**：线上版仍是 20/21（挂的那道还是 Log4j，没被这次放宽救回来），闸门版 21/21。只有这样才能确认分数变化来自代码，而不是来自我们把尺子锯短了一截。

同一批回答里，`on` 模式答出了 CVE-2026-34477~34481 与修复版本 2.25.4，NVD 侧确认为 2026-04-10 发布的同一批——这正是需要联网的那一类题：**不联网时的正确行为是承认本地没这批条目，而不是替现实下结论**。

### 那些"可疑编号"到底是不是幻觉？三批回答逐条拿去权威源验了

自动判据只能看来源标题和 URL，编号若出现在搜索正文片段里而标题没带，就会被标成可疑。这是保守告警，不是结论，所以我们把线上版那一轮 42 次回答里出现的 26 个可疑编号（off 1 个 + on 25 个，去重）逐条核了一遍——脚本留在 `scripts/verify-suspects.mjs`，别人换一批题也能重跑（`EVAL_JSON=` 指定留档）：

**16 个 CVE 编号逐条查 NVD 官方 API（`services.nvd.nist.gov/rest/json/cves/2.0?cveId=`），全部真实存在，且描述与回答里说的产品一致**——例如 CVE-2026-34477 的描述直接写明它是 CVE-2025-68161 那次修复引入的回归；CVE-2026-119977 确为 WordPress Core RCE；CVE-2026-83542 确为 Apache OFBiz 的代码注入；CVE-2026-96951 是 Windows Shell 的安全功能绕过（不是打印后台，回答里也是这么限定的）。NVD 无 key 时限流约 5 次/30 秒，脚本按 7 秒间隔串行请求并留了 503 重试。

**5 个 CWE 编号查 MITRE 官方定义页**（`cwe.mitre.org/data/definitions/<n>.html`，判定要求页面 200 **且正文真的含该编号**，否则只拿到 200 也算不过）：CWE-116 *Improper Encoding or Escaping of Output*、CWE-259 *Use of Hard-coded Password*、CWE-602 *Client-Side Enforcement of Server-Side Security*、CWE-787 *Out-of-bounds Write*、CWE-798 *Use of Hard-coded Credentials* 全部命中。

**5 个 ATT&CK 技术编号查 MITRE 官方技术页**，4 个命中（T1078 Valid Accounts、T1133 External Remote Services、T1195 Supply Chain Compromise、T1566 Phishing），**1 个没过——T1214**：ATT&CK 官方页面返回 200 但正文里没有这个编号，它是我们本地库里的一个历史条目，标的是 `credential-access`。这就是又一个真缺陷：

5. **把别的阶段的技术塞进用户问的阶段。** 问"初始访问阶段有哪些技术"时，`on` 模式不仅把 `credential-access` 的 T1214 列进了初始访问，还顺手给它起了个不存在的中文名"利用第三方应用"。语义检索捞进近似条目是常态，靠提示词叫模型"注意阶段"仍然是讲道理。现在改由代码判断：问题点名阶段时，带阶段标注而阶段不符的**非锚点** attack 条目直接不进上下文（精确锚点、用户自己写了编号的、以及没有阶段标注的都不动，滤空则退回原集合——宁可给近似资料也不把能答的题变成拒答），资料行上把 `ATT&CK 阶段：xxx` 原样写出来，并禁止给资料没给的中文名自编。

顺带这条验证也纠正了我们自己的一处误读：第一版脚本对 CWE 只判 HTTP 200，而 MITRE 的 404 页同样返回 200——指标看着"全过"，其实是判据没生效。阶段过滤能不能落地，取决于线上 `match_documents` 到底返不返回 `metadata`：我们拿真实 embedding 直接调了这个 RPC，确认每行都带 `metadata.tactics`（如 `["credential-access","collection"]`），过滤才有牙——**否则这段代码是空转的，而它看起来完全正常**。

同一批回答里还有第二类更深的问题：

6. **把"NVD 新收录"说成"已被确认在野利用"。** 同一段 `on` 回答把 CVE-2026-83542（OFBiz 代码注入，编号真实、CVSS 与描述也对）列进了"已被确认在野利用"清单，而 NVD 的 `cisaExploitAdd` 是空的——它不在 KEV 目录里。这类错误比编编号更隐蔽：每一条事实都对，只有把它们连起来的那句结论是模型加的。本地库的 KEV 条目正文有固定前缀 `在野利用（CISA KEV）｜…｜KEV 收录：日期`，于是"在野利用"改由代码给出证据清单：只有正文带该标注的编号进清单，进不了清单的编号只能表述为"NVD 已收录，是否在野利用未经 KEV 确认"。

结论修正为：**26 个编号里没有一个是凭空捏造的编号，但有 1 个（T1214）在当前 ATT&CK 版本里查不到、且被贴错了技术名和阶段**，另有 1 个（CVE-2026-83542）编号对、结论被模型加戏。"编号真实"和"引用正确"是两件事，后者才是安全场景里的硬指标，所以判据和验证脚本都留在仓库里。

修完这五处之后，用同一套题、同一份判分代码把闸门版在本地完整跑了两遍（`docs/eval-archive/local-guards-run1-2026-11-12.json`、`local-guards-run2-2026-11-12.json`），可疑编号分别是 23 个（off 1 + on 22）与 17 个（off 2 + on 15）。两份留档都逐条重验，`EVAL_JSON=` 换一份就能重跑，两遍的结果都是**全部命中权威源**：第一遍 16 个 CVE 对 NVD、4 个 CWE 对 MITRE 定义页、3 个 ATT&CK（T1078 Valid Accounts、T1195 Supply Chain Compromise、T1566 Phishing）；第二遍 13 个 CVE、3 个 CWE、1 个 ATT&CK（T1583 Acquire Infrastructure）。T1214 在两份留档里一次都没再出现——阶段过滤把它挡在上下文外面了，这是能对上号的因果，不是"这次模型刚好没犯"。

两遍的可疑编号数量差了 6 个，也不是判分变松：把两份留档逐条对齐数过——T1078、T1195、T1566、CVE-2026-119977 这几个第一遍被标可疑的编号，在第二遍的 42 条回答正文里出现次数是 **0**，而两遍的引用来源总数一模一样（都是 283 条）。也就是说分数差来自模型这一遍压根没提这些技术，不是判分器闭眼了。这种波动本身就是我们要留原文的原因：同一份代码、同一套题、同样的引用条数，可疑编号能量出 22 也能量出 15，只看一个数字什么也判断不了，必须能翻回回答正文逐条对——这也是为什么判分留档把 `answer` 一起存下来。

**然后我们意识到验的还是不够。** 上面这套只回答"编号存不存在"，不回答"编号和名字是否配对"。于是加了 `scripts/verify-id-name-pairs.mjs`：把回答里 `名称（T编号）` 和 `T编号 名称` 两种写法都抽出来，拿本地库 867 个 attack 条目的官方名做对照，机械抓三类问题——同一条回答里一个编号挂多个名称、一个名称挂多个编号、以及回答写的英文名与官方名不符。两份留档各 42 条回答跑下来这三类都是 0 处。但 0 不代表不存在：抽查同一道"初始访问阶段"题的另一次采样时，我们亲眼看到 `供应链攻击（T1566）` 和 `网络钓鱼（T1566）` 出现在同一篇回答里（供应链攻击是 T1195），那次 sampling 恰好写法躲开了正则、也没进留档。所以这条的诚实结论是：**模型自编技术名的毛病，闸门能压住（资料行现在原样带 `ATT&CK 阶段：xxx` 且禁止编名），但没到可以写成"已消除"的程度**——判分脚本能抓的是自相矛盾，抓不到"只出现一次的错配"。

7. **闸门把事实算对了，模型可以不听——而且是在联网那一侧。** 上面那张表里，闸门版第二遍 `on` 比线上低的那一行就是它。这道"2026 年被 CISA 确认在野利用的微软 Office 漏洞"：线上版答出 CVE-2026-21509（KEV 收录 2026-01-26）与 CVE-2026-124194，判通过；闸门版第一遍把 21509 写成"虽被列入 KEV 目录，但资料未说明其在野利用的具体情况"——编号还在，判分器按包含关系判通过，结论其实已经错；第二遍干脆不提 21509，只留 124194，直接判不合格。第一反应是"闸门那一轮没把 21509 算进证据清单"，我们写了个探针去证实（`dev/probe-kevgate.mjs`：连问三次同一道题，打印检索回来的本地资料与 `kevFacts` 的原文），**结果把这个猜测证伪了**：三次检索完全一致（5 条 Microsoft Office 条目，正文全部带 `在野利用（CISA KEV）` 前缀），`kevFacts` 三次都明确输出"标注的编号：…CVE-2026-21509（收录 2026-01-26）…"。也就是说闸门把正确的清单喂进去了，模型照样在 `on` 模式里把它降级或丢掉，同时照单收下网络结果里的 124194——而我们查了库，**124194 和 83542 在本地库里是 0 行**，它根本不在 KEV 快照内。今天把这道题在本地**留档**重跑：`on` 采 10 次、10 次全都列出 21509 并给出 KEV 收录日期（这三句都由 `dev/check-kev-samples.mjs` 从留档正文重算，不是终端里数一眼——留档字段 `hasKevDate` 的正则当时太窄，只认 `2026-01-26` 不认"2026年1月26日"，所以批量留档那 6 次里字段只有 2 次为真，而正文 6 次全给了日期；照正文数才是 10/10，所以我们把"以正文为准"写进了脚本注释）（`dev/kev-on-1.txt`~`3.txt` + `dev/kev-on-batch.json` + `dev/eval-grep-check.json`），`off` 采 4 次也全部正确（`dev/kev-off-batch.json`）。连同两份留档那 2 次，`on` 一共 12 次采样、2 次不照闸门说：这就是"把事实算出来喂给它"能做到的程度——比讲道理强（同一个判分器下 `off` 的 Log4j 全局否定已经被堵住了、两遍都是 21/21），但不是保证。顺带这次核查还纠正了我们自己写进稿子里的一处误判——原来那段"两次捞回的本地资料不同"是拿一个有 bug 的探针测出来的（它 embedding 调用失败却没报错，检索直接返回空集），真实情况是检索稳定、波动来自模型侧。留档只存回答正文和来源条数、不存每轮的检索上下文，所以"那一次模型看到的是什么"其实无法回溯，这也是我们接下来要给评测留档补上来源标题清单的原因。还有一个真实的结构性缺口留着：本地 KEV 是 2026.11.09 版的快照（目录版本号记在 `functions/lib/chat.ts:193` 的注释里；这一句早先写成了"2026-11-10"，那是把 124194 的 `dateAdded` 当成快照日期了，本轮照注释改回），快照之后才收录的条目（124194 就是，`dateAdded` 2026-11-10）在 `off` 模式下永远无法本地确认，只能靠现查 CISA 目录。方案想清楚了还没写：`on` 模式的 KEV 判定改成现查目录（带 TTL 缓存的只读请求，按编号给"在/不在 + dateAdded"），并把闸门的清单从"提示词里的一段话"升级成对回答的硬校验——列进在野利用清单的编号必须逐个出现在清单里，否则当场拒答这一条。没实现、没测，所以一个字也不进成绩表；但它的**负面效果**（第二遍少的那 1 题）已经进了，这是诚实的部分。

顺带这次的探针还推翻了一个我们自己先说出口的解释。前面有一版稿子写的是"同一道题两次捞回来的本地资料集合不同（DashScope embedding 有波动），所以回答跟着变"——听起来很顺，而且是拿一个探针"测"出来的。真相是那个探针写错了：它 embedding 调用失败却没检查返回值，检索于是返回空集，`kevFacts` 当然说"没有任何条目带 KEV 标注"。改正后先连测三次、今天下午又用 `dev/probe-kev-on-batch.mjs` 留档重跑 10 次（`dev/kev-on-1.txt`~`3.txt`、`dev/kev-on-batch.json`、`dev/eval-grep-check.json`）：每次都是同样 5 条本地资料、`sources` 里每次都含 CVE-2026-21509，`kevFacts` 每次都列出包括 21509 在内的全部带标注编号；`mode=on` 的波动发生在模型这一侧，不是检索这一侧。**空集和失败长得一模一样，而它给的理由听起来完全可信**——这就是为什么每个探针都要先把"拿到几条、请求状态是什么"打出来：我们差点把一次工具层的 bug 当成产品层的因果写进作品帖。同类的事在回归套件里也撞到过一次：`stats` 那条用例本地红、单独连测线上三次全绿，根因是 `count()` 把上游失败兜成了 0（详见本节前面"其一是真缺陷"那一段，今天下午又现场复现了一次：`dev/test-run5.log` 里分类求和 956 ≠ total 5397）。判分争议要能翻原文，工具结论要能翻请求日志，两者是一个道理。

第 8 处坑是今天下午才浮出来的，它改变的是我们怎么描述"联网"这件事：

8. **`search_used` 是"上游搜索插件执行过"的标志，不是"给得出可核验来源"。** 今天下午这道 KEV 题的 `mode=on` 采样里 `web_sources` **10 次全是 0 条**（这 10 次由 `dev/check-kev-samples.mjs` 逐条重算：7 次读结构化 `nWeb` 字段，3 次读 txt 留档里 `--- web sources ---` 那一段——该段无条件打印，空着就是 0 条；早先我只数过带字段的那 7 次，"10 次全 0"这句话当时其实只核到 7 次），可响应照样是 `search_used: true`、`coverage: "mixed"`，`note` 照样写"结合本地知识库与网络检索作答"；界面上网络来源区块因为列表为空不渲染（`src/components/ChatPanel.tsx:232`），`note` 却无条件显示（同文件 261 行）——访客看到的就是一句"结合了网络检索"而一条都点不开。我们把请求直接打给 DashScope 原生协议定性（`dev/probe-websearch-shape.mjs`）：`usage.plugins.search` 是 `{"count":1,"strategy":"max"}`，而 `output.search_info.search_results` 是**空数组**——搜索插件确实跑了，上游这次没返回来源清单，我们的清洗函数拿到的是空集、没吃掉任何东西。换 4 条不同问题、`auto` 与 `on` 两种模式，同样 0 条。但同一台 harness 在 14:47 那一轮 21 道 `on` 题的网络来源每条是 1~5 条，所以这是今天下午新出现的外部条件变化，不是我们把代码改坏了。它有两个直接后果：① 回归套件里 `chat：响应含联网搜索契约字段` 从绿转红，因为它断言 `web_sources.length > 0`，等于把"插件执行成功"和"搜索返回了来源"混成了一件事；② 现在再跑整套 21 题 `on`，"触发联网 21/21"仍然成立而每行 0 条来源，跟 14:47 那轮不是同一种测量条件——所以我们没有用今天的运行去替换前面那张表的数字。想清楚但还没写的修法有两处，都会动用户可见文案和一条已发布用例的期望值，所以先记在这儿等确认：`search_used 且 web_sources 为空`时 `note` 必须改成"已发起网络检索，但上游未返回可核验来源，本次回答仅依据本地资料"；用例改成断言"字段齐备 + 空来源时不得声称结合了网络检索"，再补一条不打网络的纯函数用例把这个措辞分支锁住。顺带这次读原文又抓到判分器的第二个盲区：`dev/kev-on-2.txt` 那一次回答的最后一句"目前无其他2026年新收录的在野利用漏洞记录。"是**没有来源支撑的全局否定**（正是本节第 3 条缺陷那一类），但时效题判据只查有没有提到 21509，于是它记满分。判分能覆盖的从来只有我们敢写成判据的那部分，剩下的得靠人把原文读完。

**第 8 条的边界在 11-14 收窄一次**（不改的话它会被读成"线上也这样"，而探针证明的是相反的事）：上面"`web_sources` 10 次全是 0 条"是 11-12 **本机 harness** 的 `mode=on` 采样，不是线上。11-14 线上探针留档 9 行每条都有网络来源（`docs/eval-archive/online-kev-2026-11-14.json`：legacy 6 行 `nWeb:2`；22:33 那 3 行两行 `nWeb:2`、一行 `nWeb:3`），"`search_used:true` 而来源清单为空"这一支在线上没有出现，所以这条缺陷目前能证明的是"标志位与来源条数不是同一件事"（上游协议层实证：`usage.plugins.search.count=1` 而 `search_info.search_results=[]`），不能写成"访客在线上点不开任何来源"。"本地未覆盖"这句话术也要按分支拆开，三支不一样：`mode=off` 且未联网时是 `functions/lib/chat.ts:356` 的"…且当前模式不联网；下列来源仅为近似条目…"，另有提示词层的固定话术两条（`chat.ts:303` 系统规则 3、`chat.ts:241` `gapFacts`），这一支不给 `nSrc` 也不联网；联网且本地不充分时走 `chat.ts:355` 的"本地知识库未有效覆盖本题，回答主要依据网络检索"（11-14 那条零编号反证样本与 22:33 的第 1 行都是这一支，`nSrc` 仍是 5、`nWeb` 仍非空）；联网且本地充分时走 `chat.ts:354-355` 那个三元的上半支，固定带一句"网络来源未经知识库校验"。探针 9 行 `nSrc` 全是 5，所以这些行都不是 `off`——**"重跑 N 次全绿/全红"这种话以后必须带上 mode 与分支，否则就是把一支的孤证当另一支的证明。**

第 9 处坑是第二天（2026-11-14）给这道旗标题建可重跑测量时浮出来的，而它先推翻的是我们自己写进计划的归因：

   那条零编号回答确实发生过，现在入库可核：`docs/eval-archive/online-kev-empty-retrieval-2026-11-14.json`（`raw` 是原始响应的逐字节副本，`provenance` 带源文件字节数与 sha256，其余摘要字段一律由 `raw` 现推；本机 `dev/` 里那份字节一致的原件仍在但不入库）。它的 5 条 `sources` 是 Adobe Acrobat、两条 Android Framework、Apple、MFA(T1556/006)，`similarity` **全是 0.3，里面没有 CVE-2026-21509**——所以 `srcHasId` 实测为 **`false`**（早先那份手抄摘要把它写成 `true`，抄的是"预期判定"而不是实测，本轮改掉）。注意 `srcHasId` 只能判来源**标题**：响应契约里的 `SourceRef`（`functions/lib/chat.ts:12-18`）只有 `title/url/category/similarity/live`，没有正文字段，所以它为真说明本地命中的标题里带该编号，为 **`false`** 却**不能证明**检索正文里没有该编号。请求条件也要对齐着看：这条反证样本是当天 20:33 的手工抓样、请求体显式 `mode:"on"`，与 legacy 那 6 行（不带 `mode`→`auto`）不是同一条件，与它同模式的是 22:33 那 3 行。
   **旧归因在此撤回，原文保留以自证**：计划初稿写的是"`mode` 默认 → `nSrc:5` 且本地检索结果里明明有 5 条含 CVE-2026-21509 的资料，正文却零编号……**这道旗标题线上答不好**"，第一版第 9 条又写成"**检索拿到了、回答没用上**"。**两句都错**，而且是被同一份留档证伪的：那份上下文里根本没有 21509 可"用"。真实的因果链是**语义检索空集 → 关键词兜底捞回 5 条不相干条目 → 判不充分 → 如实拒答**：`chat.ts:133` 是 `embedding ? await vector(...) : []`（embedding 取不到就当没有语义结果，不报错也不报警），`chat.ts:137` 的兜底只在 `docs.length === 0` 时接替，`kb.ts:134` 把兜底条目的 `similarity` 写死成 0.3，而 `isLocalSufficient()`（`chat.ts:67-71`，门槛 `SEMANTIC_FLOOR` 0.65 在 `:65`）对 0.3 必然判不充分；这道题的题干没有任何精确锚点（`chat.ts:112-131` `collectLocal` 里那几条锚点路线都要编号或战术词：T####、`CVE-\d{4}-\d{4,7}`、CWE-、arXiv 版本号、TACTIC_HINTS），所以"充分"这一支只能靠语义路径拿到。**空集和失败长得一模一样，而它给出的理由听起来完全可信。** 这个差别直接决定后面两个方案的价值边界：对回答正文做**生成后**硬校验挡的是"编号真、结论错"和"有证据却不说"，它挡不住这一次——那一次的上下文里没有 21509，断言集是空的，没东西可校验；能在这条路径上救回这道题的是生成前注入（Task 4 Step 4）与现查 CISA 目录（Task 3），且后者**不许把本地检索结果当触发条件**，否则同一次语义空集会同时让两层都闭嘴。
   还有四处判据看不见、但评委对着入库文件就能数出来的事：① `CVE-2026-21514` 在两个 run 合计 **0/9** 从未被提到，而判据照样给绿——探针只把 21509 写进判据，21514 与 124194 是观察项（`watch`），不进退出码；目录口径必须同时写：2026.11.13 的真目录里"Microsoft + Office"按 `dateAdded` 落在 2026 年有 **5 条**（21509、21514、124194，外加两条今年才收录的 2009 年老编号 CVE-2009-0238、CVE-2009-0556），按 CVE 编号年份算才是 **3 条**，只写"3 条"就是藏掉口径；这批行（含 `dateAdded`/`dueDate`/`knownRansomwareCampaignUse`）现在入库在 `docs/eval-archive/kev-catalog-2026-office-2026-11-14.json`，此前它只有被 gitignore 的 `dev/kev-feed-cache.json`。上一版这里写"第三条本地没有，**这 6 次是靠网络那一侧把它补上的**"——对着入库正文逐行数，124194 只出现在 legacy 的**第 1、3、4、5 行（4/6）**，第 2、6 行压根没提它，22:33 那 3 行是 2/3；"靠网络补上"对提到它的行成立，对整批不成立，这句在本轮被改成计数。② `hasDate` 只看日期串在不在、不看它挂在哪个语义位置：22:33 第 1 行那句"该漏洞于2026年1月26日被修复"就满足了判据，而目录里的 `2026-01-26` 是 `dateAdded`（KEV 收录日），尺子分辨不了"收录日期"与"修复日期"。③ `degraded` 是一份字面词表的抽查，不是完整性闸：legacy 第 2 行的"但**未明确指出**其在2026年被CISA列入在野利用状态"与第 5 行的"**无权威信息**"都不在词表里，于是两行都记绿（词表漏抓的是第 2、5 行，漏答 124194 的是第 2、6 行，有交集但不是同一批）。所以"合规"在这份留档里的意思只有"编号 + 日期串 + 类型词出现且没踩到那几个字面措辞"，**它不等于"答对了"**，也不等于"目录内的都答全了"。④ 本地 KEV 快照停在 2026-11-09，124194（`dateAdded` 2026-11-10）在 `off` 模式下永远无法本地确认，只能现查目录。
   发布通道没通之前，线上跑的仍是加闸门之前的 prompt，上面提到的修法（现查目录、生成前注入、清单硬校验）一件也没上去——**所以这条只能以"实测到的非确定性 + 一处被证伪的归因 + 三处尺子盲区"存在，一个字也不得写成已修**；同理，充分分支的 `note` 固定写着"网络来源未经知识库校验"，这句在发布前后都不该被当成已解决。

11-12 那一轮 21 题评测直接改变了三处实现：CWE 精确锚点、"域外可答题不判拒答"（问 WiFi 密码怎么找回，助手正常给建议是对的，底线是别冒出安全编号）、以及上面那个日期基准注入。基线报告保留在 `docs/eval-report-baseline.md`，改前改后都能看到。

**上面那句"判分器只查有没有提到 21509"，当天就补了一半，但补的方式值得单说。** KEV 那道题的判据加了 `title`：编号之外还要求回答里的漏洞类型和官方名对得上（NVD 描述是 "Reliance on untrusted inputs in a security decision in Microsoft Office … bypass a security feature locally"，本地库与 MSRC 的标题都是 *Microsoft Office Security Feature Bypass Vulnerability*）。加完判据的下一步不是跑分，是**证明它会判红**——`node scripts/eval.mjs --selfcheck` 用 7 条合成样本同时钉住两个方向（3 条必须红：编号对但类型挂错、压根没提到该编号、旧日期未加限定；4 条必须绿，含"无 `title` 判据的题目不受影响"这条防误伤），7/7 过、退出码 0、不发一次网络请求。为什么值得为一条判据写自检：这份判分器今天已经骗过我们两次，一次假阳性（整篇匹配的 `failIf` 把合格的诚实回答判成违规），一次假阴性（正则写成字符串时反斜杠被转义吃掉，`\d` 变成 `d`，永远匹配不到）——新加判据却不证明它能判红，就等于允许它空转。

**还要说清楚这条判据没做过的事。** 它是**预防性收紧，不是修某个已测到的缺陷**：`dev/check-title-criterion.mjs` 把四份留档（线上版、闸门版两遍、当前 `docs/eval-report.json`）里那道题的 8 行逐行重算，旧口径=提到编号、新口径=编号且类型对得上，结果是 **0 行判定翻转**（脚本退出码非 0 就代表翻转过）。更要紧的是我自己在写这条判据时留下的一处错：代码注释里一度写着"线上留档里出现过把 CVE-2026-21509 写成 Azure Portal 前端 CSRF 的回答"——对全部留档 grep `CSRF|跨站请求伪造` 是 **0 命中**，那句话是我把**来源标题当成回答内容**读出来的，注释已按实测改掉。这是今天第二次把"没落档的说法"当成结论（第一次是"`off` 4 次里 1 次过度推脱"那句，同样已撤回），而同一条毛病我们在正文里批评了模型三回。

## 七、Qoder 在这个项目里干了什么

除了托管与边缘函数，开发过程基本是"描述意图 → 得到能跑的代码 → 用真实请求验证"：Function 分层重构、pgvector 检索问题定位、回归与评测脚本、以及这份作品帖里的每个数字都来自实际执行结果。我们刻意让每一条声称都可复现——README 里写的数据来源，都能在 `data/` 下找到对应的采集脚本。
